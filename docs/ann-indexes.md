# ANN (HNSW) indexes for semantic search

Decision record and ops notes for issue #81. Implementation: `backend/app/ann.py`.

## Decision

The pgvector embedding columns (`article_embeddings`, `catalog_entry_embeddings`,
`browser_history_document_embeddings`, `dislike_rule_embeddings`) **stay
dimension-less `Vector()`**. The dimension follows whatever
`OPENAI_EMBEDDING_MODEL` is configured, and rows for two models — two
dimensions — coexist while the worker re-embeds after a model switch. That
flexibility was the original reason there were no ANN indexes at all: pgvector
cannot build HNSW on a column without a declared dimension.

Instead of pinning the dimension (option 1/2 in the issue), each searched table
gets a **partial HNSW index on a cast expression**:

```sql
CREATE INDEX hnsw_article_embeddings_<hash> ON article_embeddings
USING hnsw ((embedding::halfvec(1536)) halfvec_cosine_ops)
WHERE model = '<configured model>';
```

- The cast supplies the dimension the column lacks.
- The partial `WHERE model = …` predicate does double duty: it keeps rows of
  any other model (whose dimension would fail the cast) out of the index, and
  it matches the `model` filter every query already carries.
- `halfvec` (fp16) halves index size at negligible recall cost and lifts the
  indexable-dimension ceiling from 2000 to 4000.

A **model switch needs no schema migration**: the worker's next cycle builds
the new model's index once re-embedded rows appear and drops the old one.
`dislike_rule_embeddings` is deliberately not indexed — its only consumer is
the threshold join in `suppressions.py` (`WHERE distance < x` across two
columns), which an ANN index cannot serve.

## Why not an Alembic migration

The index expression depends on the configured model and its dimension —
deployment configuration, unknowable to a static revision. The worker calls
`ann.ensure_indexes()` every cycle instead: a no-op when the index matches, a
build when rows for the configured model exist without one. If an
autogenerated migration ever drops these (they are not in the SQLAlchemy
metadata), the next worker cycle recreates them.

## Query-side contract

- Call sites opt in with `ann.knn_distance(column, query_vector)`, whose cast
  matches the index expression, and `await ann.relax_scan(session)` before
  executing. The latter sets `hnsw.iterative_scan = strict_order` for the
  transaction so the joins/filters layered on the KNN don't thin the candidate
  pool to `ef_search` (default 40).
- Only `ORDER BY … LIMIT` shapes qualify. Two sites intentionally stay exact:
  the catalog "recommended" ranking (no LIMIT — an HNSW scan ends early and
  would drop rows) and the dislike-rule threshold join.
- `related_articles` and history search were restructured around index-served
  KNN pool subqueries (`RELATED_KNN_POOL`, `HISTORY_CHUNK_POOL`) because their
  outer ordering (NER-boosted score, per-document `min(distance)`) is not a
  bare distance. The history pool keeps the `user_id` filter *inside* the KNN
  subquery — the filtered-search caveat from #81 — so the iterative scan keeps
  pulling until the pool holds that user's chunks.

## Requirements and ops

- **pgvector ≥ 0.8** (compose and CI ship `pgvector/pgvector:pg16`, currently
  0.8.x). On older servers `ann.py` builds nothing and sets no GUCs; every
  query falls back to the exact scans this codebase always did.
- **Index builds block writes to that table** (plain `CREATE INDEX`, worker
  context). At the ~100k-row scale where the index starts mattering, expect a
  build in the low minutes. `ensure_indexes` builds **serially** with
  `maintenance_work_mem = 512MB` for its session: the parallel build sizes
  shared-memory segments by `maintenance_work_mem`, which overflows the 64MB
  `/dev/shm` of a default Docker container ("could not resize shared memory
  segment" — observed on the compose stack). Serial keeps the graph in
  private memory. Once a table outgrows 512MB of graph (~150k rows at 1536
  dims), builds degrade to the slower on-disk phase — raise the value in
  `ann.py` alongside real memory, or raise the container's `shm_size` and
  revisit parallel builds.
- Benchmark + recall check: `cd backend && PYTHONPATH=. uv run python
  scripts/benchmark_ann.py --rows 100000` seeds a scratch `newsread_bench`
  database and prints exact-vs-indexed timings, recall, and whether EXPLAIN
  uses the index. The synthetic vectors are clustered (1000 centers + noise)
  on purpose: uniform random vectors concentrate every pairwise distance
  around 1.0 at high dimension, turning top-K into a giant tie-band and any
  recall figure into noise (measured: 0.2–0.35 "recall" on uniform data vs
  1.000 on clustered — the former is tie-shuffling, not lost neighbors).
- Models beyond 4000 dimensions are skipped (HNSW's halfvec ceiling) and stay
  on exact scans, logged once per worker cycle attempt.
